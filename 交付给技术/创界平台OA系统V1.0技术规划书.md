**版本：** V1.0

## 1. 规划结论

创界平台原型确定为 **OA 系统 V1.0 的业务与交互基线**。本期建设围绕总经理工作台、六个上线业务中心、财务必要协作节点以及跨部门协作，将目标、任务、审批、人员、文件和业务办理纳入同一套账号、权限、流程和审计体系。原型中的页面与演示数据用于说明业务意图；是否达到可上线状态，以服务端规则、真实接口、数据迁移和验收结果为准。

建议沿用现有 Java 17 后端和 Vue 3 前端，按模块化单体方式推进，先打通统一身份、公共待办和两条代表性流程，再逐中心交付。现有仓库已有部分业务代码，但不能据此认定原型范围已经实现；各模块须按本书的验收条目逐项核对。

| 范围 | V1.0 处理方式 |
|---|---|
| 总经理工作台、项目运营、产品供应链、创业者发展、AI科技、仓储履约、视觉内容 | 按原型建设业务页面、表单、待办与数据权限；创业者发展含人事行政与创业者管理两个独立业务域 |
| 公共能力 | 统一登录、组织人员、角色与数据范围、目标任务、审批待办、通知、文件、知识、搜索、审计和调度 |
| 财务 | 保留采购、盘点等流程所需财务处理节点；完整财务工作台和财务业务板块留待后续版本 |
| 外部系统 | ERP、企业微信、文件服务、本地模型按已取得的真实接口分批接入；未联通时明确显示待接入状态 |
| 手机端 | V1.0 优先支持待办查看、审批、任务反馈和文件上传的响应式页面；复杂维护以桌面端为主 |

“V1.0”是本系统版本，不代表另一套独立工程的 V2 代码。原型里的模拟角色、模拟 ERP 查询、演示金额、固定日期和浏览器本地存储均不作为生产实现。

## 3. 业务能力与关键流程

### 3.1 统一协作

总经理工作台呈现经营与管理视角；中心工作台只展示授权范围内的数据。目标按公司、中心、个人逐级分解；任务按“下发—接收—执行反馈—成果提交—验收—完成”推进。员工进度最高为 99%，验收通过后系统记为 100%。跨部门审批统一进入公共待办，业务详情与公共待办调用同一服务端命令，避免出现两套结果。

每个待办必须指向唯一业务单据、流程实例和当前节点。当前处理人或候选组才可操作；经办人与审批人分离。驳回要求原因和整改期限，退回实际表单继续办理；延期申请与批准单独留痕，不暗改原承诺日期。撤回、终止、作废均保留历史，不记为正常完成。

### 3.2 人员档案与账号

新增人员先建立档案，工号由服务端生成并保证唯一，创建表单不要求人工填写。档案初始为待到岗；到岗确认前不得赋予可登录的 OA 权限。到岗时核对本人身份、组织岗位、上级和任职信息，再执行账号开通及权限分配，并保存每一步的结果与经办记录。原型把“到岗确认”和“系统权限开通”表现为两个步骤，生产流程应分别记录状态；即使由同一页面连续办理，也不能把到岗动作视为已成功开通账号。离职时生成交接清单，完成交接后停用账号。

创业者人员档案与普通员工档案分域维护，共享自然人身份关联，不混用业务状态。立项由总经理审批；立项后的账号、协议、资产等事项分别完成并消除待办。

### 3.3 中心业务

- 项目运营：店铺经营视图、商品库存查询、选品、采购申请、平台服务和销售任务。项目与店铺对应，主理人可负责多个项目。
- 产品供应链：供应商图片库、清仓、潜力品、产品开发和商品生命周期；商品与库存等外部字段标记来源和同步时间。
- 仓储履约：按 ERP 数据生成盘点任务，记录差异、负责人复核和财务处理；周期任务由后台调度，不依赖打开页面。
- 视觉内容：任务分配、制作、成果上传与审核，文件按业务编号和版本保存，不覆盖历史成果。
- AI科技：研发需求、任务流转及受控知识问答；模型建议不能直接执行审批、付款或权限变更。

上述业务页面以原型为交互基线，但字段、节点及完成条件须在流程清单和数据字典中逐项落地。

## 4. 技术架构

采用“Vue 3 前端—Java 17 服务端—关系数据库/文件服务—外部集成”的分层架构。现有工程可复用登录、组织权限、通用页面和部分业务模块；新增规则应落在服务端业务模块，避免复制到多个页面。流程状态、审批判断、编号生成、灯色计算和数据范围都由服务端统一计算。

| 层次 | 责任与边界 |
|---|---|
| 前端 | 工作台、表单、待办、移动适配；显示服务端返回的权限与状态，不自行决定能否审批 |
| 业务服务 | 单据状态机、流程节点、事务、幂等校验、领域权限、操作审计 |
| 数据层 | 员工/组织、业务单据、流程实例、附件元数据、通知与审计；数据库类型以现有工程兼容性和运维能力确定 |
| 文件服务 | 稳定文件 ID、校验值、版本、密级、下载鉴权；业务表不保存可供用户直接访问的共享盘路径 |
| 集成层 | ERP、企业微信、文件服务器、本地模型；记录请求号、结果、重试与对账信息 |
| 调度与运维 | 周期任务、超时变灯、提醒、同步、备份、监控和恢复 |

一期不必为每个中心拆独立微服务。先用清晰模块边界和单一权威状态降低跨流程一致性成本；实际并发、部署规模和故障域达到拆分条件后再评估。数据库、缓存、消息和模型组件的最终产品选型须经现有环境核实，不把原规划里的建议直接当作已采购事实。

## 5. 流程与时限设计

流程模板要有版本号，运行中的实例沿用发起时的版本。实例记录业务编号、发起人、当前节点及处理人、节点和整体期限、业务状态、附件、意见、事件日志。每次提交、通过、驳回、补件、延期、撤回、终止要在一次事务中完成业务状态与待办更新；接口使用业务幂等键和数据库唯一约束防止重复单据。

业务自然日按北京时间计算，截止日到 23:59:59；节点期限不得晚于整体期限。延期获批后至少保留已经产生的黄灯，红灯不能降级；驳回延期仍保留原期限。普通审批默认 2 个自然日，最终起算事件待业务确认。红灯规则存在“满 3 个自然日”与“逾期 72 小时”的表达差异，测试用例和代码在第 13 节确认后统一。定时任务负责扫描和通知，页面刷新不能改变期限。

流程变更应先形成“流程模板—节点责任人—期限—表单—异常路径—验收案例”六项清单，再实施。管理规则按已确认口径：新制度、模板和关键变更由总经理审批；日常维护及已签协议归档由创业者发展中心总监处理；创业项目最终立项由总经理审批。

## 6. 身份、权限与数据治理

一人一账号、一人可有多个角色；每次操作记录真实账号、当时角色及组织上下文。权限由功能权限、数据范围、流程节点、文件范围共同判定，后端查询和下载均校验行级权限，不信任前端传入的员工 ID 或中心 ID。临时授权需有期限、范围与审批记录；账号停用后立即禁止访问。

组织员工档案是人员主数据；业务单据保存稳定人员 ID 和必要历史快照。ERP 是交易与库存的权威来源，本系统保存同步快照与时间。涉及身份证、银行卡、薪酬、已签个人合同等敏感数据要单独授权，不进入全员知识检索。数据迁移先盘点来源、映射、去重、试导入、对账，再正式导入；保留来源主键、批次、失败原因和抽查记录。

## 7. 文件、知识与本地模型

附件记录文件 ID、所属对象、版本、原名、大小、类型、校验值、上传人、密级和授权范围。已生效制度、模板及已验收成果不可原位覆盖，版本废止与审批可追溯。上传校验格式、大小和恶意文件；下载走服务端鉴权，敏感导出进入审计。数据库与文件须分别备份并演练恢复。

知识入库由获批准的制度、模板、流程成果及人工整理资料构成，保存来源和版本；草稿、废止文件及个人敏感档案默认不进入公共空间。检索先做权限过滤，再检索和生成回答；回答显示可点击来源、版本和更新时间，无证据时明确说明。模型只调用受控只读业务 API，不直接操作数据库或执行审批。原规划中的 4090 服务器是待核实资源条件，实际模型性能和可用性须通过样本问答验证。

## 8. 集成方案

ERP 对接商品、店铺、销售、退款、库存和入库等字段，先确定权威字段、增量方式、频率、限流与对账口径；同步失败保留日志并支持重试与人工补同步。企业微信用于身份映射及待办提醒，消息包含业务链接但不暴露敏感详情。若账号平台或 OA 外部接口不可用，应记录“开通待办/失败”及凭证，不伪造开通成功。外部接口都应有超时、重试上限、幂等标识和故障告警。

## 9. 安全、部署与运维

测试与生产环境分离；公网入口经 HTTPS 和身份认证，数据库、文件及模型服务不直接暴露公网。高权限账号启用更严格的认证与导出控制，权限变更和管理员操作留痕。应用监控覆盖服务健康、接口错误、调度失败、同步滞后、磁盘容量、备份结果。备份介质不能只放在生产服务器同一磁盘；恢复目标与保留期限在部署设计时确定。

性能目标不以原型本地运行速度推断。上线前以实际用户数、文件量、ERP 数据量和外网条件进行压测，确定常用页面响应时间、批处理窗口及告警阈值。原规划中的“约 20 人”“2 秒页面”等数字可作为待验证目标，不能视为已测结果。

| 2 核心协作 | 总经理工作台、目标任务、项目运营与供应链核心流程、ERP 基础同步 | 实际角色权限、驳回、延期和同步对账通过 |
| 3 中心扩展 | 创业者、仓储、视觉、AI科技、通知及历史数据迁移 | 各中心业务验收和迁移对账签收 |

每阶段交付代码、数据库迁移脚本、接口说明、测试结果及操作文档。发布采用测试环境验收、问题修复、生产备份、发布、回滚预案和业务复核的闭环；未通过业务验收的模块不以“页面已完成”计入交付。

## 11. 验收标准

1. **流程：** 每条核心流程覆盖正常通过、驳回重提、超时变灯、延期、撤回/终止、重复提交、处理人变化；公共待办与业务页结果一致。
2. **人员：** 创建档案自动分配唯一工号；未到岗不可登录；到岗与账号开通分别留痕；开通失败可重试且不重复创建账号。
3. **权限：** 普通员工、中心负责人、主理人、总经理、财务处理人分别验证菜单、列表、详情、附件、导出和直接 URL；停用后权限立即失效。
4. **数据与文件：** ERP 同步可对账、可重试、不重复；文件可下载、校验、保留旧版本，越权不可访问；迁移数量和关键字段与来源核对。
5. **知识与模型：** 不同权限用户只获得各自有权来源；废止或撤权内容不再作为有效引用；无证据时不编造，模型不可越权操作。
6. **运维：** 定时任务、备份、告警和恢复演练有记录；生产环境可按预案回滚。

## 12. 项目风险与控制

- **原型覆盖不等于生产需求闭环。** 按业务流程逐条确认字段、异常路径、责任人与验收案例，禁止只按页面数量估算进度。
- **外部接口不确定。** 提前取得 ERP、企业微信、账号平台、文件服务器的测试环境和字段文档；接口缺失时单列依赖，不把模拟数据当作上线能力。
- **人事与知识数据敏感。** 上线前完成数据分类、权限矩阵、导出审计和恢复演练。
- **跨中心流程复杂。** 以统一待办和单一权威状态承接，流程版本冻结后再联调，减少多处状态不一致。
- **范围与工期偏差。** 六个上线中心加财务协作节点及公共能力的范围较大，实施应按阶段验收；人员配置、实际工期与成本须依据详细工作量及接口条件单独核定。

## 13. 待确认决策

以下事项不应由开发人员猜测，须由业务负责人和技术负责人在相应阶段开始前签字确认：

| 决策项 | 需要确认的口径 |
|---|---|
| 红灯计算 | “超过截止日满 3 个自然日”与“逾期 72 小时”选择一种，并给出跨月、节假日和 23:59 边界案例 |
| 审批期限 | 默认 2 个自然日从提交、节点分配还是处理人签收起算 |
| 关键变更 | 哪些制度/模板修改属于须总经理审批的关键变更 |
| 账号开通 | 到岗确认后由谁开通、系统自动还是人工办理、失败补偿与重试责任人 |
| 基础资源 | 真实人员和岗位清单、数据库及文件服务器现状、4090 机器配置、外网访问方案 |
| 外部接口 | ERP、企业微信、账号平台的可用接口、字段权限、测试账号和同步频率 |
| 数据与合规 | 历史档案迁移范围、敏感字段权限、文件保留期限、审计日志保留期限 |

## 14. 版本维护
